# How a policy changes

The same steps apply to a new policy and to a substantive change to an adopted one. The aim is that no affected group is surprised.

1. **Proposal.** A written proposal with numbered decisions, so comments can refer to them. It is presented at a CSC meeting, and its page here is marked *Proposed*.
2. **Comment period, two weeks.** Notice goes by mail and Slack to the subsystem and working-group lists, and to the physics working groups through the physics coordinators. Comments come through a feedback form or by mail.
3. **Written replies.** Every substantive comment gets a written reply, recorded with the change it caused, usually as an appendix to the write-up. Each commenter also gets a personal reply.
4. **Revision.** The proposal is revised and its version number goes up.
5. **Ratification at CRAB.** The page is marked *For ratification* while CRAB considers it, then *Adopted*.
6. **Publication.** The adopted text, or a summary with a link to it, is merged here. Checklists, templates and CI checks that implement it follow.

Two weeks is also the window [dependency change control](dependency-change-control.md) uses before a release, for the same reason.

## Versions

Each policy write-up carries a version number. Version 1 is the text opened for comment. Each revision put to CRAB, and each later change, increases it. The snapshot shows the current version, and each policy page lists its history.

## Editorial changes

Typos, broken links and clarifications that do not change what anyone must do are ordinary pull requests, reviewed by the policy's owner. They do not change the version.
